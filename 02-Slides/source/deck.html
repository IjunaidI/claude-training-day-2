Block 2 · Context
Context is a room filling up.
Every prompt, reply, file and command output sits in one finite window, re-read on every turn. As it fills, early decisions stop carrying weight.
Illustrative shape, not a benchmark. /context shows your own numbers.
  • 01
    BlendingTwo rules from two subsystems merge into one nobody stated.
  • 02
    StalenessDecision v1 is still in the room next to v3. Sometimes v1 wins.
  • 03
    DropoutThe constraint from minute ten stops being applied at all.
  • 04
    ConfidenceNone of it is announced. The answers stay fluent.

SAY: "Imagine someone walks you through procurement, payroll, inventory and tax for four hours with no notes. By hour three you are not stupid. You are full."

SAY: "Models fail the same four ways. Blending, staleness, dropout, and the worst one: it doesn't feel wrong from the inside."

SAY: "Yesterday's fixes still apply: /context to see it, /clear between tasks, subagents for noisy reading. Today adds the big one: put durable facts in a file."

Block 2 · The fix
A document does not get tired.
SPEC.md is read at the start of every run, at full weight. It is the same 625 lines for everyone in this room.
The requirements live in a conversation that is already fading.
The requirements live in a file, in Git, reviewable in a pull request.

SAY: "Nobody's version drifted because their session went long, and nobody's is better because they explained it more patiently."

SAY: "That is also why a spec can be reviewed: it exists before the code, as a diff someone can comment on."

Every soft word in a requirement is a decision you have handed to the agent. Replace it with something a reviewer can check.

Make sure it works

Block 3 · Guardrails
Protect the contract.
The builder may read the spec. It may never edit it. That is a deny rule, not a sentence in a prompt.
.claude/settings.json · committed
{
  "permissions": {
    "allow": [ "Bash(dotnet *)", "Bash(curl *)",
               "Bash(git status *)", "Bash(git diff *)",
               "Bash(git add *)", "Bash(git commit *)" ],
    "deny":  [ "Edit(SPEC.md)", "Edit(lab/**)",
               "Edit(.github/**)", "Bash(git push *)",
               "Bash(rm -rf *)" ]
  }
}
  • 01
    Deny Edit(SPEC.md)It can't "fix" the spec to match its code.
  • 02
    Allow the build toolsAn hour of work without two hundred prompts.
  • 03
    Plan, then auto-accept editsApprove the plan once. Review each milestone in git diff.
Day 1, Block 10: guidance is followed nearly always. Enforcement always. The spec gets enforcement.

Block 5 · Independent review
Never let the author grade the exam.
The session that wrote the code has its own reasoning in context. Asked to review, it re-reads its intent and under-reports.
THE SESSION THAT BUILT IT
A COLD SUBAGENT
/review-build dispatches assetdesk-reviewer: Read, Grep, Glob only. It can find. It cannot fix.

SAY: "Yesterday: a subagent inherits nothing from your conversation. That was a limitation in Block 6. Here it is the whole point."

SAY: "The skill is short and it says why: if the same context reviews its own code, it reviews its own reasoning, and the counts stop being comparable."

Block 5 · How a good review reads
Point at a line, or say nothing.
  • 01
    A file and a line"Consider whether error handling is robust" is a feeling, not a finding.
  • 02
    Cite the rule, not your tasteSPEC.md §4.6, or a skill name. No rule, no finding.
  • 03
    Absence is not a defectNo tests, no interfaces, no CI: §2 forbids them. Correct here.
  • 04
    One decision, one findingFive components injecting the repository is one finding, five locations.
  • 05
    Find, don't fixThe moment you start fixing, you stop looking. The reviewer has no write tools.
These are the reviewer agent's instructions. They are also how to review a colleague.

DO: open .claude/agents/assetdesk-reviewer.md on the projector. It is 40 lines. Point at "Report only what you can point at with a file and a line."

SAY: "Rule 3 is the one humans break most. Flagging something the spec forbids means you are reviewing the spec, not the build."

Block 5 · The evidence
An audit is only as good as its rulebook.

The twist

Same unchanged code, reviewed with 2 rules: 3 findings. With 9 rules: 5. The code didn't decay. The lens widened.

BucketThe fix
BOUNDARYA skill makes the decision
QUALITYA skill writes the standard
SPECFix the code
A clean report means "nothing I was told to look for". Never "nothing wrong".

SAY: "We ran this build many times with one variable: which skills were in .claude/. Numbers are the typical shape from those dry runs. A live build is not deterministic; what repeats is which bucket moves."

SAY: "The twist is the lesson. An audit that finds nothing has told you about its rulebook, not about your code."
